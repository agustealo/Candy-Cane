# Candy Cane documentation manifest

## Screenshot authority

Public-facing Candy Cane screenshots are generated by the deterministic `tests/docs-showcase.sh` runtime and `tests/browser/docs-showcase.mjs` capture pipeline.

The showcase runtime uses a clean WordPress installation, the current Candy Cane theme, real posts, pages, categories, comments and menus, deterministic editorial artwork, and pinned Chromium/Playwright tooling. External images and synthetic theme mockups are not part of the screenshot authority.

The `Docs Showcase` workflow owns freshness. On same-repository pull requests it synchronizes regenerated assets into `docs/screenshots/`. On `master` it regenerates the showcase and byte-compares it with the committed files, failing if the public documentation images are stale.

## Canonical visual assets

The following committed files under `docs/screenshots/` are the documentation authority:

- `desktop-home.png` - primary README and repository hero
- `desktop-single.png` - editorial single-post presentation
- `desktop-page.png` - page and sidebar presentation
- `tablet-home.png` - responsive tablet home grid
- `mobile-home.png` - compact home experience
- `mobile-single.png` - compact editorial experience
- `desktop-keyboard-overlay.png` - keyboard-visible image-card overlay
- `showcase-manifest.json` - generated route, viewport and capture metadata

Regression screenshots from `tests/browser-artifacts/` remain engineering evidence and must not be used as public marketing imagery.

## Documentation surfaces

`README.md` uses `desktop-home.png` as the primary visual and selected feature captures for product context. `docs/SCREENSHOTS.md` is the complete visual gallery and explains what each asset demonstrates.

The whole `docs/` tree is marked `export-ignore`, so visual documentation never enters the customer-installable Candy Cane ZIP. The runtime Docker context excludes it as well.
